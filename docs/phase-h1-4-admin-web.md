# CampusStay H1.4 — Admin Web Dashboard frontend

Completed locally on 2026-10-23. **Frontend only; not deployed or connected to privileged services.** Docker recovery and H1.3 backend integration remain on hold.

## Architecture and isolation

The standalone application is in `admin-web/`, inside the existing repository for reviewability, with no npm workspace or dependency hoisting. It owns its package/lockfile, node_modules, Next/Turbopack root, TypeScript, ESLint and a separate path-filtered CI workflow. Next.js App Router 16.4.2 and React/React DOM 19.2.3 have compatible official npm peer ranges; Node 25.8.1 was used locally and CI targets Node 24. TypeScript 6.0.3 is compatible with the chosen tooling. Direct versions are pinned.

Runtime packages: Next 16.4.2, React 19.2.3, React DOM 19.2.3, Lucide React 1.61.0. Development packages: TypeScript 6.0.3, ESLint 9.39.4, eslint-config-next 16.4.2, tsx 4.23.15, Playwright 1.64.1, @types/react and @types/react-dom 19.2.2, @types/node 24.10.0. Prettier 3.9.10 was used temporarily on new web files only, without adding it to either dependency manifest.

Only two existing files were edited: the root `tsconfig.json` and `eslint.config.js`, each gaining the admin-web exclusion while preserving prior edits. A new narrow `metro.config.js` preserves Expo defaults and excludes absolute/project-relative admin-web paths, including web node_modules and build caches. The root Expo package and lockfile, mobile source, native project, authentication, document privacy, migration and cloud configuration were not edited.

Next generated `admin-web/AGENTS.md` during development. It is retained; the installed version's relevant routing, proxy, environment and TypeScript documentation was reviewed. Generated `next-env.d.ts` is ignored and regenerated by typecheck/build.

## Pages and design

- Overview: derived synthetic counts, pending queue, status distribution chart, recent sample/session activity.
- Manager Applications: applicant/business/location search, five-state filtering, newest/oldest/name sorting and details links.
- Application detail: contact/business/location/declaration, evidence metadata, timeline, internal preview notes, and reason-bound approve/request-information/reject previews with confirmation.
- Property Reviews: safe original residence illustrations, illustrative Single/Shared information and separate, disabled property moderation controls.
- Users & Managers: synthetic students, applicants, approved managers and suspended/revoked access examples; expandable details, no account operations.
- Audit Logs: actor/action/target/time/outcome/reason views with filters; sample/preview outcomes are explicit, with SAST timestamps.
- Settings: read-only integration boundaries and an in-memory reset.
- Sign-in: visibly disabled visual prototype with no credential collection.
- Reusable shell, sidebar, mobile modal navigation, breadcrumbs, status badges, avatars, section headings, loading/empty/error states and feedback.

The implementation mirrors CampusStay navy #0F1B2D, blue #2563EB and existing neutral/status colors. It serves existing Outfit/Inter font copies locally with OFL licenses, uses Lucide icons, rounded cards and restrained shadows, and adds no decorative gradients or underlined navigation. Keyboard focus, selected navigation names, skip link, native dialog focus/escape behavior, reduced motion/transparency preferences and accessible table scroll regions are supported.

Responsive fixes include intrinsic card grids, wrapped headers/forms, contained screen-reader-only table labels and timestamps that reflow rather than escape phone widths. Text-scaling tests assert the computed root font size: 16px, 20.8px and 32px. Initial tests found and repaired overflow and corrected a lower-specificity test style that had failed to reliably apply enlargement.

## Data and H1.3 compatibility

The exact local migration and mobile verification DTO were inspected. Typed projections represent applications, statuses, decisions, reviewer identity, evidence metadata, events and manager authorization states. Compile/runtime tests check DTO compatibility and the local review RPC signature.

The preview fixture, pure local transform/filter adapter, provider and presentation are separate from the future adapter, which rejects all operations. No SDK or Supabase project configuration is installed in the web application. No live-schema claims are made.

Important distinctions:
- Review uses the prepared `cs_manager_review(p_application, p_revision, p_decision, p_reason)` shape; stale/duplicate/self reviews and invalid reasons are refused in preview.
- A preview approval changes one example application's status/history only. It grants no role, approves no property and sends no message.
- Email/reviewer labels need a future identity projection; they are not invented H1.3 application columns.
- Internal notes are memory-only UI drafts. H1.3 has no private-notes field; its review reason is applicant-visible.
- Drafts demonstrate presentation states but are not an assertion that reviewer RLS permits access to real drafts.
- No private file content, object path, signed/public document URL or real audit event is generated.

## Security boundaries

`ADMIN_MOCK_MODE=1` requires explicit development opt-in and is checked on the server. Production build/server phases reject the flag, even with a misleading NODE_ENV override. Normal production admin requests return HTTP 403/private-no-store. Both proxy and a server-only page/layout guard deny access; query strings/cookies are not authorization inputs. There is no production authentication or admin allowlist, user metadata authorization, role bootstrap or credentialed adapter.

All preview pages display “Demo preview — no changes saved to Supabase.” Synthetic records live only in the layout provider, survive ordinary client navigation and reset on full reload. The prototype sign-in form is disabled. Notifications and profile identity are clearly unavailable/illustrative. CSP restricts network sources to self; framing, forms and device capabilities are disabled. Inline framework scripts/styles remain permitted; authenticated integration should separately review a nonce strategy.

## Remaining limitations

- Linux CI was prepared but not executed here. No Safari, physical-device or spoken accessibility check is claimed.
- Native export results are recorded separately below; bundling never establishes device execution.
