## Endpoint and environment safeguards

- Explicit `H13_MODE=local-staging` is mandatory, including offline plans.
- The only API target accepted is the literal `http://127.0.0.1:55321`. The database descriptor is exactly `postgresql://postgres@127.0.0.1:55322/postgres`, contains no password, and is not used as a SQL connection string. SQL control instead uses the exact named local database container's `psql` over stdin.
- Hosted URLs of **any** project, project references, Management tokens, remote DSNs, different ports, localhost aliases, LAN addresses and emulator aliases are rejected. This covers CampusStay and Mumus Property without relying on a two-project denylist.
- HTTP permits only local Auth/REST/Storage/Functions paths; redirects are disabled and redirect responses rejected. No DNS alias is accepted for the host target.
- Child processes receive an environment allowlist. Cloud Supabase/Expo variables, database overrides, AWS credentials, proxy settings, Node preload options and arbitrary CLI overrides are not inherited. CLI profiles/keyring and Docker config are isolated under the staging workspace; the Docker engine target is the fixed local Desktop Linux named pipe. `EXPO_NO_DOTENV=1` prevents Expo dotenv discovery if a future approved launcher uses this environment.
- A separate `runtimeEnvironment` adds only the three workspace-generated Auth settings supported by pinned source: `SUPABASE_AUTH_PUBLISHABLE_KEY`, `SUPABASE_AUTH_SECRET_KEY`, `SUPABASE_AUTH_JWT_SECRET`. It never imports an app dotenv file.
- The workspace rejects symlink/junction redirection, alternate config JSON, dotenv files, project links, version-pin files and application migration/schema execution paths. Preparation refuses existing workspaces instead of resetting them.

The app's original `.env.local` deliberately still targets cloud. **Do not run the ordinary Expo launcher for local testing.** The prepared mobile launcher supports `--plan` only and refuses `--launch`. A separately isolated client/session namespace, per-request guard and reviewed emulator/device-to-host bridge are still needed. Production HTTPS/key validation and app authentication behavior were not weakened.

These controls prevent accidental remote targeting through the prepared entry points. They are not protection against an administrator intentionally bypassing them or running unrelated scripts. No runtime network containment has been established while Docker is stopped.

## Port binding and outbound isolation

Pinned CLI source builds `-p <port>:<container-port>` with no host IP for PostgreSQL, Kong and Mailpit. That alone does not guarantee loopback privacy.

The prepared alternative is a **dedicated user-defined bridge** named `campusstay-h13-local-loopback`, with `com.docker.network.bridge.host_binding_ipv4=127.0.0.1`, IPv6 disabled and `--internal` to prevent ordinary container outbound routing to hosted services. Supply this network through the supported `--network-id` flag. It affects only this future network, not global Docker settings. Docker documents this per-network binding option; actual Windows Desktop behavior remains a runtime gate.

Future command shape, **not executed or currently approved**:

```powershell
docker --host npipe:////./pipe/dockerDesktopLinuxEngine network create `
  --driver bridge --internal `
  --opt com.docker.network.bridge.host_binding_ipv4=127.0.0.1 `
  --label com.supabase.cli.project=campusstay-h13-local-staging `
  campusstay-h13-local-loopback
```

Before any service starts, verify the network's ownership, driver, options, internal status and lack of other attachments. Reject existing resource collisions. A monitored trial must verify actual mappings immediately and stop if any service publishes `0.0.0.0`, `::`, an unexpected port or attaches to another network. Accept only Kong 127.0.0.1:55321→8000, PostgreSQL 127.0.0.1:55322→5432 and Mailpit 127.0.0.1:55324→8025. The seven service identity/binding policy is implemented and unit tested.

The internal bridge deliberately blocks dependency downloads from Edge containers. Host-side approved image pulls remain possible. Whether the pinned Edge image starts entirely from cached/bundled resources is **not verified**. If it needs external imports, stop and prepare an explicitly reviewed offline dependency cache/bundle; do not silently remove internal isolation. Application-function npm dependencies need the same treatment before later integration tests. A loopback binding protects LAN exposure; it does not hide local services from other host processes.

No firewall changes were made. If supported per-network binding is not honored, the trial remains blocked. A fallback would require approval for narrowly scoped Windows/Hyper-V firewall restrictions for these ports/interfaces and validation of Docker Desktop forwarding behavior. A blanket inbound rule is not assumed to protect every Docker/WSL path. No such firewall command is proposed for automatic execution.

## Startup rollback and volume preservation

The pinned legacy CLI calls rollback with `deleteVolumes=isFreshVolume`, including errors/interrupts during startup and health checks. Therefore the **first newly created project database volume may be automatically removed** on failure. Existing-volume rollback follows a different preservation branch; that is not an unconditional guarantee about every possible resource/failure. The CLI was not patched, nor was startup executed to test destruction.

Before a future first start, inventory exact container, network and volume names/labels and refuse **any** collision. Approval must explicitly permit the CLI's automatic cleanup of only resources newly created for that disposable trial. It must not permit deletion of pre-existing data, unrelated resources or manual pruning. If this limited cleanup is not acceptable, standard CLI startup remains blocked; use a separately reviewed volume-preserving orchestration approach instead.

No reset, `--no-backup`, `--all`, `docker system prune`, volume removal or global WSL shutdown is included. Normal project-scoped `supabase stop` retains named volumes. On failure preserve private logs, record OOM/exit/health data, inventory what survived, and stop for review; do not repeatedly restart or reset.

Pinned CLI source also fixes the local PostgreSQL bootstrap password rather than supporting a `db.password` TOML setting. It is a development default, **not a copied live password**, and is not printed here. Independently generated Auth/API credentials do not change that database default. A trial approval must acknowledge this loopback-only bootstrap limitation or defer startup for a different orchestration/password strategy. No unsupported password override is claimed.

The suite retains synthetic data and disables readiness in `finally` after ownership is established; if containment fails, inspect and explicitly pause this local instance before any retry.
